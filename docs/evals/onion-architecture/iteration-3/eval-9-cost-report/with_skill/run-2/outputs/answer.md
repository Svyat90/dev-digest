Причини двох проблем такі. Повільність (pass 6, N+1): `service.ts` у циклі `agents × days` викликає `repo.costForDay`, тобто на 90 днях це 90 запитів на кожного агента (10 агентів дають 900 послідовних `await`). Виправлення: додати в `repository.ts` один метод, наприклад `costByAgentAndDay(workspaceId, from, to)`, з `GROUP BY agent_id, date_trunc('day', ran_at)`, `sum(cost_usd)` і фільтром `workspace_id`. Він має віддавати рядки, згруповані за агентом, а `listAgents` залишається поза циклом. Опційно можна додати індекс на `(workspace_id, ran_at)`. Сервіс тоді лише розкладає ці рядки по днях у чистій функції (кандидат на `helpers.ts`) і не робить жодних запитів у циклі. Показ $0.00 (порушення правила "null = невідомо, 0 = безкоштовно"): `Number(row?.total ?? 0)` у `costForDay` перетворює відсутність даних (`sum()` повертає null) на 0. Ця ж нуль-підстановка потрапляє в `totalUsd` і `perDayAvgUsd`, а середнє ділиться на всі `days`, навіть на порожні. Виправлення: репозиторій повертає `null` для дня без запусків, `costUsd: number | null` у DTO, сума береться лише по днях з даними, середнє ділиться на кількість днів з даними (або `null`, якщо даних немає взагалі), а UI показує "—" замість $0.00. Додаткові зауваження: (1) дні рахуються від `from` як від довільного моменту, а не від UTC-півночі, тому межі діб зсунуті відносно підписів `toISOString().slice(0,10)`; варто нормалізувати `from` до початку доби UTC. (2) `routes.ts` сам робить `new CostReportRepository(container.db)`, а тип відповіді (`AgentCost`) лежить у service і не оголошений як `response` схема. Краще тримати конструювання в композиційному корені або контейнері та додати контракт у `vendor/shared` (разом із клієнтською копією) і `response: { 200: ... }`. Tenancy у запитах дотримано (`workspaceId` скрізь), транзакції не потрібні. Після змін перевірити `pnpm arch:check`, а для чистої функції розкладання по днях написати unit-тест без БД.

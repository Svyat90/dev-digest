0)` — `sum()` повертає `null` для днів без запусків, і репозиторій збиває «немає даних» у `0`, а сервіс далі додає це в `totalUsd`/`perDayAvgUsd` (ділить на `days`, а не на кількість днів із даними); це порушує доменне правило репо «`null` = невідомо, `0` = безкоштовно» (`specs/review-flow.md`, `parseAggregateCost`). **Виправлення, по кільцях:** (1) інфраструктура — один метод `repository.costByAgentAndDay(workspaceId, fromUtcDay, toUtcDay)` з одним агрегатом `GROUP BY agent_id, date_trunc('day', ran_at)`, що фільтрує за `workspace_id` + діапазоном і повертає `{agentId, day, costUsd: number | null}` через `parseAggregateCost` (sum як `string | null` обробляється лише в репозиторії), плюс `listAgents` залишається; за потреби індекс `(workspace_id, agent_id, ran_at)` через drizzle-kit (міграції не руками); (2) домен — чисті функції в `helpers.ts` (нормалізація `from` до UTC-доби, побудова списку днів, заповнення прогалин `null`, `totalUsd` як сума лише відомих значень, `perDayAvgUsd` по днях з даними або `null`, якщо даних немає) з unit-тестами без БД; (3) застосунок — `service.report` лише: listAgents + один запит агрегату + виклик чистих функцій, без циклів з I/O; (4) контракт — `AgentCost` з `costUsd: number | null` винести з `service.ts` у `src/vendor/shared/contracts/` (і в копію `client/src/vendor/shared`, бо вона вже розійшлась — перевірити обидві), а в UI рендерити `null` як «—»/«no data», а не `$0.00`; (5) презентація — у `routes.ts` додати `response`-схему з `costUsd: z.number().nullable()` і, за скілом, збирати `CostReportService` з вузьких `Deps` (репозиторій тут створюється в роуті через `new CostReportRepository(container.db)` — це допустимо лише як тимчасово; краще винести створення в композиційну сторону). Архітектурно залежності спрямовані правильно (роут → сервіс → type-only репозиторій, drizzle лише в репозиторії), тож `arch:check` не зламається, а базлайн чіпати не потрібно.

# Labels -> onion: що створювати (і чого не створювати)

Я прочитав `server/CLAUDE.md`-конвенцію через скіл `onion-architecture` і код модуля. Коротко: **запропонований набір (LabelsService + доменний шар + use-case клас на ендпоінт) для цього модуля — це over-engineering, і я раджу його не створювати.** Нижче — чому, що реально варто зробити і що робити, якщо ви все одно хочете повний шар.

## Що є зараз

`modules/labels` — чистий CRUD із 4 ендпоінтами (list / create / patch / delete):

- `routes.ts` — zod-схеми, `getContext`, один виклик `repo.*`, `NotFoundError` для `null`/`false`. Бізнес-розгалужень немає.
- `repository.ts` — усі Drizzle-запити, кожен метод приймає `workspaceId`, повертає `Label` DTO (а не рядок БД), мапер `toLabel` поруч.
- `db/schema/labels.ts` — таблиця; змін не потребує.

Тобто кільця вже розділені: presentation -> infrastructure, `routes.ts` не імпортує `drizzle-orm` чи `db/schema`, tenancy-скоупінг у сигнатурах репозиторію.

## Чому не service / domain / use-case-на-ендпоінт

Правило скіла (розділ 1): для CRUD-модуля (`workspace`, `settings`) достатньо `routes.ts` + `repository.ts`; «не вигадуйте сервіс, що лише пересилає виклики». Сервіс/домен виправданий, коли є: правило, продубльоване у двох хендлерах; хендлер, що розгалужується по бізнес-стану; хендлер, що викликає два порти (БД + GitHub/LLM); тест, якому потрібен Postgres лише заради обчислення. У labels жодного з цих сигналів немає:

| Пропонована річ | Що вона містила б | Вердикт |
|---|---|---|
| `LabelsService` | `list -> repo.list`, `create -> repo.create`, ... — чисте прокидання | Не потрібен: один вхід (HTTP), нуль оркестрації |
| Доменний шар | Нічого: немає ні обчислень, ні статусів. Регекс кольору та довжина імені — це валідація на краю (zod у `routes.ts`) | Порожній шар |
| Use-case клас на ендпоінт (4 класи) | По одному рядку делегування кожен | Мінус 4 файли + 4 конструкції без виграшу; Seemann: додатковий use-case шар коштує більше, ніж повертає, коли є одна точка входу й мало логіки |
| Нові порти | Немає зовнішньої системи | Не потрібні |
| `UnitOfWork` | Кожна операція — один statement | Не потрібен |

Також `arch:check` уже зелений для цього модуля; нова структура нічого не додала б до enforcement.

## Що я б реально зробив (малі кроки, `pnpm arch:check` зелений після кожного)

Нічого структурного — але в модулі є дві справжні дрібниці, варті виправлення, бо вони про коректність, а не про «шари»:

1. **Конфлікт унікальності при PATCH.** Індекс `labels_ws_name_uq (workspace_id, name)`. `create` робить upsert (перефарбовує існуючу назву), а `PATCH` на ім'я, що вже існує, кине помилку Postgres `23505` -> 500. Виправлення: у `repository.rename` ловити unique violation і кидати доменну помилку, або (простіше) додати `ConflictError` у `platform/errors.ts` (зараз є лише AppError/NotFound/Validation/ExternalService/Config) і мапити його в `app.ts` у 409. Помилка кидається з репозиторію/маршруту, `reply.code()` не чіпаємо. Додати `*.it.test.ts` на репозиторій (rename на зайняте ім'я).
2. **Назва `rename`.** Метод змінює і name, і color; перейменуйте на `update` (лише всередині модуля, 2 місця).
3. **(Опційно) Створення репозиторію один раз на плагін** уже так і зроблено (`new LabelsRepository(container.db)` у тілі плагіна, не в хендлері) — залишити як є. Якщо хочете суворіше, можна брати `container`-репозиторій, але для CRUD-модуля скіл цього не вимагає.

Тести: `*.it.test.ts` для репозиторію (list-порядок за name, create-upsert, scoping по workspace, remove чужого id -> false) та один `app.inject()` на маршрути. Domain-юніт-тестів немає, бо немає domain-коду.

## Коли варто повернутися до service/domain

Додавайте `service.ts` (і чисті функції в `helpers.ts`), коли з'явиться хоч одне з: ліміт міток на workspace або правила кольору/зарезервовані імена, які діють у кількох місцях; прив'язка міток до PR/findings з багатотабличним записом (тоді `UnitOfWork`, див. `references/transactions.md`); виклик зовнішнього порту (напр. синхронізація з GitHub labels). Тоді шаблон такий (мінімальний, один service, не клас на ендпоінт):

```
modules/labels/
  routes.ts       // zod, getContext, ОДИН виклик service-методу
  service.ts      // class LabelsService { constructor(deps: { repo: LabelsRepo }) } - методи = use case-и
  helpers.ts      // чисті правила (normalizeName, isReservedName) + unit-тести без БД
  repository.ts   // як зараз; service залежить від його типу, а не від Drizzle
```

Use case = **метод** сервісу, а не окремий клас; в цьому репо так само влаштовані `reviews`, `agents`, `repo-intel`.

## Підсумок

- Створити файлів: **0** структурних. Правки: `ConflictError` (+ мапінг у `app.ts`), обробка `23505` у `labels/repository.ts`, перейменування `rename` -> `update`, плюс integration-тест.

- Якщо вирішите, що все ж потрібно (напр. для консистентності), скажіть — розпишу повний план файл за файлом, але з застереженням, що це додає ~6 файлів без жодної поведінки.

# labels: чи потрібна повна onion?

**Коротко: ні. Не раджу створювати `LabelsService`, доменний шар і use-case клас на кожен ендпоінт.** Модуль уже onion-сумісний, а ці шари тільки додали б код, який нічого не робить.

## Що є зараз (прочитано)

- `db/schema/labels.ts` — таблиця Drizzle з унікальним індексом `(workspace_id, name)`. Це інфраструктура, тут усе на місці.
- `modules/labels/repository.ts`:
  - усі запити Drizzle;
  - кожен метод приймає `workspaceId` і фільтрує по ньому;
  - мапер `toLabel` перетворює рядок на DTO, тож назовні виходять не сирі рядки.
- `modules/labels/routes.ts`:
  - zod-схеми params, body і response;
  - `getContext` для tenancy;
  - один виклик методу репозиторію на хендлер;
  - `null` / `false` з репозиторію перетворюється на `NotFoundError`;
  - немає `drizzle-orm`, `container.db` у запитах чи `Schema.parse(req.body)`.
- Репозиторій створюється один раз на плагін, а не на запит.

Правило залежностей виконано: route -> repository -> db. Проти правил `routes-do-not-touch-the-db` та `application-does-not-know-the-orm` порушень немає. Це CRUD-модуль, як `workspace` чи `settings`. Для таких скіл прямо каже: `routes.ts` + `repository.ts` достатньо, сервіс, який лише пересилає виклики, вигадувати не треба. Єдине, чого route не може, це ходити в Drizzle напряму, і тут цього немає.

## Чому не створювати запропоноване

Скіл називає ознаки, коли сервіс або доменна функція виправдані. Жодної з них у labels немає:

| Ознака | У labels |
|---|---|
| Правило дублюється у двох хендлерах | ні |
| Хендлер розгалужується за бізнес-станом | ні, лише "не знайдено -> 404" |
| Хендлер викликає два порти (БД + GitHub/LLM) | ні, тільки БД |
| Тест на розрахунок вимагає Postgres | розрахунків немає |

Наслідки запропонованого:

- **`LabelsService`** містив би чотири методи-перенаправлення на репозиторій. Це "service that only forwards calls".
- **Доменний шар** не має що містити. Єдина "логіка" це валідація (`trim/min/max`, hex-колір), яка вже є в zod на краю. Скіл вимагає парсити один раз на краю й не дублювати у внутрішніх шарах.
- **4 use-case класи** при одній точці входу (HTTP) і нульовій логіці дають 4 файли за звичайним `await repo.x()`. Це якраз той випадок, який описує Seemann, коли додатковий use-case шар коштує більше, ніж дає.
- Рефакторинг модуля без причини суперечить скілу: модуль чіпають, коли є причина, а не тому що він "ще не onion".

## Що можна зробити, якщо хочеться дрібних покращень

Вони необов'язкові, кожен окремий і не ламає `pnpm arch:check`:

1. **Перейменувати `rename` -> `update`** у `repository.ts` і в `routes.ts`. Метод міняє і name, і color, тож назва вводить в оману.
2. **Задокументувати upsert.**
   - `POST /labels` для наявного імені перефарбовує мітку, а не повертає 409. Це єдине неочевидне правило модуля, і воно живе в SQL (`onConflictDoUpdate`).
   - Якщо це навмисно, залишити коментар на методі `create`.
   - Якщо ні, змінити поведінку на конфлікт з `AppError`. Це продуктове рішення, не архітектурне.
3. **Винести `Label` / `LabelDto` у `vendor/shared/contracts/`.** Робити лише коли клієнт реально використовує цей контракт. Тоді не забути про копію `client/src/vendor/shared`, яка вже розійшлась. Зараз тип дублюється між `Label` у репозиторії та `LabelDto` у routes.
4. **Перевірити `pnpm arch:check`** у `server/`, щоб зафіксувати, що модуль чистий.
5. Тести за типологією з `TESTING.md`:
   - `repository.it.test.ts` проти реального Postgres: scoping за workspace, upsert, повернення `false` / `null` для чужого id;
   - `app.inject()`-тест на 404 і валідацію.

## Коли повертатися до сервісу

Створити `service.ts` (з `Deps`, а не з `Container`) варто, коли з'являться реальні правила. Приклади:

- ліміт кількості міток на workspace;
- заборона видаляти мітку, що використовується в PR;
- синхронізація з GitHub labels (два порти);
- каскадне оновлення кількох таблиць, яке треба обгорнути в транзакцію через `UnitOfWork`.

Тоді порядок такий: чиста функція правила + unit-тест без БД, потім метод сервісу, потім метод репозиторію, потім тонкий route.

# digest-publish: причина дублів і «фантомної доставки», структура, виправлення

Прочитано: `onion-architecture/SKILL.md`, `references/audit.md` (сім проходів), `references/transactions.md`. Також звірено порт `GitHubClient` у `vendor/shared/adapters.ts` і таблицю `digests` у `db/schema/ops.ts`. `server/INSIGHTS.md` не відкривався (обмеження бенчмарку).

## 1. Причина багу (прохід 5 — порядок ефектів), блокер

`DigestPublishService.publish` (`service.ts`) робить: LLM → **INSERT дайджесту з `deliveredTo`** → **`gh.postReview`** → `finish` (`periodEnd`).

- Рядок із `deliveredTo = owner/name#N` записується ДО виклику GitHub. Якщо `postReview` падає (мережа, 403, rate limit, рестарт процесу), у БД лишається «доставлений» дайджест, а коментаря в GitHub немає. Це перша скарга.
- Повтор запиту (клієнт або користувач повторює POST після помилки або таймауту) створює ще один рядок і ще раз викликає `postReview`. Ідемпотентності немає, тож якщо перший виклик дійшов до GitHub, а впав `finish` або відповідь загубилась, виходять два коментарі. Це друга скарга.
- Стан не відображає правду: `deliveredTo` означає «куди збираємось», `periodEnd` використано як маркер завершення. Явного статусу в таблиці `digests` немає, тому повтор не бачить, що вже зроблено.
- LLM-виклик перед записом теж не захищений: повтор знову платить за LLM.

## 2. Що ще не так зі структурою (проходи 1–4, 7)

1. **Конструювання (прохід 2) і імпорти (прохід 1), `routes.ts`.** Маршрут робить `new DigestPublishRepository(container.db)` і імпортує `./repository.js`, а той тягне `drizzle-orm` і `db/schema`. Модуль не CRUD, у нього є сервіс, тож презентаційний шар не має знати репозиторій і `container.db`. Правило `routes-do-not-touch-the-db` це, найімовірніше, зловить, а `container.db` у route суперечить SKILL §5. Репозиторій треба збирати в композиційному корені (метод/геттер у `platform/container.ts`, наприклад `container.digestPublish`), а маршрут має отримувати вже готовий сервіс.
2. **Порти (прохід 3).** `postReview` існує в `GitHubClient`, тож тут порядок. Але для ідемпотентності порт треба розширити (див. фікс). `llm: () => container.llm('anthropic')` з жорстко вписаною моделлю `claude-haiku-5-5` у сервісі: модель і провайдер — конфіг/константа, а не рядок усередині use case.
3. **Pick-типи.** `repo: Pick<DigestPublishRepository, ...>` у `Deps` робить сервіс залежним від *класу* інфраструктури (type-only import теж порушує залежність, SKILL §3, `tsPreCompilationDeps`). Потрібен вузький інтерфейс-порт, який описує сам сервіс (або в core), а репозиторій його реалізує. Крім того, `Pick<GitHubClient,'postReview'>` нормальний, це вузький порт.
4. **Тенантність (прохід 4).** Методи репозиторію приймають `workspaceId`, `getRepo` і `finish` теж. Тут добре. Зауваження: `getRepo(workspaceId, pull.repoId)` ок.
5. **Вихід (прохід 7).** Репозиторій повертає сирий `DigestRow`, а маршрут віддає його як є (`reply.send(digest)`) без `response`-схеми, тобто тече кожна колонка, включно з майбутніми. Потрібна контрактна схема `Digest` у `vendor/shared/contracts/` (і копія в client, див. кореневий CLAUDE.md), `response: { 201: DigestSchema }` і мапер рядок → DTO в репозиторії.
6. **Чиста логіка.** Побудова `deliveredTo` і промпта — чисті функції: винести в `helpers.ts` з юніт-тестом без БД.
7. **Транзакція.** Тут не потрібна одна велика транзакція: ефект зовнішній, а SKILL §6 забороняє тримати транзакцію відкритою навколо зовнішнього виклику. Потрібна послідовність маленьких безпечних станів.

## 3. Виправлення

### 3.1 Схема і стани (міграція генерує drizzle-kit, руками `migrations/**` не чіпати)
Додати в `digests` колонки `status` (`'pending' | 'posting' | 'delivered' | 'failed'`), `pull_request_id`, `github_review_id` (nullable), `delivered_at`, `error` (nullable), та унікальний індекс на `(workspace_id, pull_request_id)` (або на ключ ідемпотентності). `delivered_to` заповнюється лише після успіху. Потім `pnpm db:generate` і `pnpm db:migrate`.

### 3.2 Послідовність у сервісі (impureim sandwich, кожен крок залишає безпечний стан)
1. Прочитати PR і репо. Якщо вже є дайджест для цього PR зі статусом `delivered`, повернути його (повтор не створює нічого).
2. LLM-підсумок (поза будь-якою транзакцією). Якщо рядок `pending` уже має `bodyMd`, повторно LLM не викликати.
3. `repo.upsertPending(workspaceId, prId, bodyMd)`: рядок зі статусом `pending` (один рядок на PR завдяки унікальному індексу, повтор підхоплює той самий).
4. Перед відправкою перевірити, чи коментар уже є. Додати в порт `GitHubClient` метод use-case-форми, наприклад `findReviewByMarker(repo, n, marker): Promise<{ id: string } | null>`, і вшити в `body` прихований маркер `<!-- devdigest:digest:{digestId} -->`. Якщо знайдено, пропустити пост (це закриває випадок «коментар дійшов, а `finish` упав»). Порядок змін: порт у `vendor/shared/adapters.ts` → адаптер в `adapters/github/` → мок в `adapters/mocks.ts`.
5. `postReview` (зовнішній виклик, без транзакції).
6. Одним апдейтом `markDelivered(workspaceId, id, { githubReviewId, deliveredTo })`: статус `delivered`, `delivered_at`, `periodEnd`. При помилці на кроці 5 зловити, виставити `failed` + `error` і прокинути `AppError` (наприклад 502-підклас у `platform/errors.ts`), щоб повтор міг продовжити з `pending`/`failed`.

Лишаються два вікна гонки: два одночасні запити (закриває унікальний індекс + перехід `pending → posting` умовним UPDATE, переможець один) і падіння між кроками 5 і 6 (закриває маркер із кроку 4). Повна exactly-once гарантія неможлива без підтримки на боці GitHub, тому йдеться про at-least-once + дедуплікацію за маркером.

### 3.3 Структурні правки
- Вузький порт `DigestStore` (інтерфейс у модулі або в core) замість `Pick<DigestPublishRepository,…>`; `Deps` не імпортує клас репозиторію.
- Репозиторій і сервіс збирає `platform/container.ts`; `routes.ts` бере готовий сервіс і не імпортує `repository.js` / `container.db`.
- Контракт `Digest` + `response`-схема + мапер у репозиторії; клієнтську копію контрактів оновити.
- Модель і провайдер винести в константу/конфіг; чисті функції в `helpers.ts`.

### 3.4 Тести
- Юніт (сервіс, фейкові Deps, без Postgres): (a) `postReview` кидає виняток → статус `failed`, `deliveredTo` порожній; (b) повтор після `failed` → один пост; (c) повтор після `delivered` → нуль викликів `postReview` і LLM; (d) маркер уже є на GitHub → пост пропущено, статус `delivered`.
- `*.it.test.ts` для репозиторію: унікальний індекс і умовний перехід `pending → posting` при двох паралельних викликах.
- Перевірка: `pnpm arch:check` (базлайн не росте), `pnpm typecheck && pnpm test` у `server/`.

Порядок виконання (кожен крок залишає `arch:check` зеленим): 1) схема + міграція + статуси, 2) порт `findReviewByMarker` + адаптер + мок, 3) перепис `publish()` на нову послідовність + тести, 4) винести збирання в контейнер, 5) контракт + response-схема.

## Підсумок за блокерами
Блокери (хибні дані): порядок «INSERT delivered → GitHub → finish» без статусу та ідемпотентності. Лише структура: route конструює репозиторій і знає `container.db`, `Pick<Repository>` у Deps, відсутня response-схема і сирий рядок на виході, захардкоджена модель.

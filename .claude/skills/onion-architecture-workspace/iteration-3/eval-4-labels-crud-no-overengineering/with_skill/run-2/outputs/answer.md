# Labels: чи потрібен повний onion (LabelsService + domain + use-case на ендпоінт)?

Прочитано: SKILL.md `onion-architecture` (розділи 1, 2, 4, 5, 11) і код фікстури. Коротка відповідь: **ні, для цього модуля це надлишково, і я не раджу створювати ці файли.** Нижче пояснення і що зробити замість цього.

## Що зараз у модулі

- `routes.ts` — 4 ендпоінти (GET, POST, PATCH, DELETE), zod-схеми, `getContext`, один виклик репозиторію на хендлер, `NotFoundError` при `null`/`false`.
- `repository.ts` — Drizzle-запити, скоповані по `workspaceId`, мапер рядок -> `Label`.
- `db/schema/labels.ts` — таблиця, унікальний індекс `(workspace_id, name)`.

Це точно форма CRUD-модуля, яку skill (розділ 1) вважає достатньою: `routes.ts` + `repository.ts`. Маршрут не імпортує `drizzle-orm` і не лізе в `db/*`, тобто правило `routes-do-not-touch-the-db` не порушене. Перевірка за чекліcтом розділу 11 проходить.

## Чому не робити те, що ти просиш

Skill прямо каже: для CRUD-модуля (`workspace`, `settings`) "не вигадуй сервіс, який лише пересилає виклики". Сигнали, що сервіс виправданий (розділ 1), тут відсутні:

| Сигнал | Labels |
|---|---|
| правило дублюється у двох хендлерах | ні |
| хендлер розгалужується за бізнес-станом | ні (лише `if (!x) throw NotFound`) |
| хендлер кличе два порти (DB + GitHub/LLM) | ні, один репозиторій |
| тест на розрахунок потребує Postgres | ні, розрахунків немає |
| багатотабличний запис / транзакція | ні |

Конкретно:

- **`LabelsService`** був би чотирма методами виду `return this.repo.list(ws)`. Єдина "логіка" — кинути `NotFoundError`, а це дві рядки в роуті.
- **Доменний шар** порожній: немає ні правил, ні розрахунків. Валідація (`trim`, `min/max`, hex-regex) — це parse на краю, її місце в zod-схемі роуту (розділ 5: "parse once, at the edge"). Окрема `Label`-сутність була б анемічною копією `LabelDto`.
- **4 use-case класи** — це 4 файли з одним викликом кожен. Seemann: додатковий шар коштує більше, ніж повертає, коли є одна точка входу і мало логіки.

Витрати: ~9 нових файлів, плюс DI/wiring, плюс тести з фейками, і нуль нових гарантій. А `arch:check` вже зелений.

## Що варто зробити (малі кроки, кожен лишає `arch:check` зеленим)

Реальні, невеликі проблеми я бачу такі:

1. **Дублювання DTO.** `LabelDto` у `routes.ts` і `interface Label` у `repository.ts` описують те саме. Якщо клієнт теж використовує цей контракт, винести схему в `src/vendor/shared/contracts/` (і перевірити копію в `client/src/vendor/shared`, вона вже розходилась), а репозиторій типізувати `z.infer`. Інакше залишити як є.
2. **Конструювання репозиторію в роуті.** `new LabelsRepository(container.db)` у тілі плагіна дозволений для CRUD (раз на плагін, не на запит), але якщо хочеш тестувати роут з фейком, додай `labelsRepo` у `platform/container.ts` (ліниво, з `ContainerOverrides`) і бери `container.labelsRepo`. Це єдина "нова" деталь, яку я б розглянув.
3. **Реальний баг, не архітектура.** `PATCH` з іменем, що вже існує в workspace, порушить унікальний індекс `labels_ws_name_uq` і, ймовірно, дасть 500. Потрібен `ConflictError` (409): ловити код Postgres `23505` у `rename` усередині репозиторію і кидати `AppError`-підклас з `platform/errors.ts`. Це доречніше за будь-який сервіс.
4. **Семантика POST.** "Створити або перефарбувати" через `onConflictDoUpdate` повертає 201 навіть при оновленні. Це продуктове рішення, варто або задокументувати, або розділити. Також дві паралельні `PATCH`/`POST` безпечні завдяки індексу.
5. **Тест.** Один `labels.it.test.ts` проти реального Postgres для репозиторію (скоуп по `workspaceId`: мітка іншого workspace не видаляється і не оновлюється) плюс `app.inject()` на 404/409. За `TESTING.md` цього достатньо.
6. Назва `rename` робить і перейменування, і зміну кольору. Перейменувати на `update` (дрібна гігієна).

## Коли повернутися до твого плану

Якщо в labels з'явиться справжня логіка, наприклад: ліміт кількості міток на workspace, прив'язка міток до PR/findings (друга таблиця, отже транзакція через `UnitOfWork`), синхронізація з GitHub labels (другий порт), каскадні правила при видаленні, тоді вводь `service.ts` з `Deps { labelsRepo, ... }` (вузькі залежності, не `Container`), чисті функції правил у `helpers.ts` з unit-тестами без БД, і лише тоді. Use-case клас на кожен ендпоінт у цьому репо не є конвенцією взагалі (application-шар тут: `service.ts`, `run-executor.ts`, `findings.ts`), тож навіть тоді достатньо методів сервісу.

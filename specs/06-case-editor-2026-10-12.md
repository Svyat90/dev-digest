# Spec: Case Editor and the skills' Evals tab
Spec ID: SPEC-06-case-editor
Status: approved
Supersedes: none
Packages: server, client
Depends on: SPEC-04-eval-pipeline, SPEC-05-eval-dashboard

## Problem and user

The people hurt are **agent authors and skill authors**. SPEC-04 builds an
agent's case set only from findings a reviewer accepted or dismissed, so the set
covers only what the agent has already found or flagged. A bug the agent has
never seen — an incident in another team, an edge case from a colleague's code
review, a regression the author is about to fix — cannot become a case at all
(course brief, design `images/16.png` › Case Editor). A case that was created
with a wrong line range cannot be fixed either; the author can only delete it
and lose it.

Skills have the same need and no place for it. A skill is shared by several
agents (`server/specs/skills.md` S2, S10), yet nothing measures whether a skill
edit made reviews better or worse; the author finds out on a real PR.

Why it matters: the dataset should grow from two sources — the history of
decisions and the author's prediction of future failures (course brief). With
hand-written cases, quick single-case checks while writing them, and the same
deterministic runs for skills, every prompt or skill change can be measured on
the cases the author cares about, not only on the ones that happened to occur.

This spec covers the Case Editor (create, edit, run one case, Run on save), the
per-case actions on the Evals tab, and the skill detail's Evals tab with runs
through an agent the user picks. Scoring, metrics, frozen inputs, concurrency
and the run record are SPEC-04's; run comparison is SPEC-05's.

## Goals / Non-goals

Goals:

- Create a case by hand from a pasted diff fragment — because cases for bugs
  the agent has never met cannot come from findings.
- Edit a case without silently breaking comparison with earlier runs — because
  a fixed case is worth keeping, but a metric change must never come from an
  unnoticed case change.
- Run one case on demand, and on save — because writing a case is a loop of
  "paste, assert, check", and a full run per check costs time and money.
- Validate everything the user types or pastes before it is stored — because a
  case that cannot be scored, or that smuggles text to the model, poisons every
  later run.
- Give each skill its own case set and runs through an agent the user picks,
  with both versions recorded — because a skill is shared and must be measured
  on its own, and a number is meaningless without the configuration that
  produced it (SPEC-04 Goals; user answer).

Non-goals:

- Re-deciding SPEC-04 semantics: matching, pass rules, noise (only findings
  overlapping a `must_not_flag` location), pooled metrics with errored cases
  excluded and not passed, the 100,000-character frozen input, at most 3 cases
  in parallel, one run per owner at a time, 10 starts per minute, code-only
  scoring. They are used as SPEC-04 defines them.
- Changing SPEC-05's "Case sets differ: N added, M removed" notice wording; this
  spec only says how an edited case is counted in it.
- Turning a finding into a skill-owned case, or moving and copying cases between
  owners — "Turn into eval case" keeps creating agent-owned cases (SPEC-04 AC1,
  AC2).
- Full file contents as case input — the review engine reviews a diff, and
  SPEC-04 AC13 limits a case's input to its frozen diff and PR title and
  description.
- Importing or exporting cases as files, and bulk editing.
- An LLM judge or any model call in validation or scoring.
- How the editor, the diff preview, contracts, tables or routes are built, and
  in what order — that is for the implementation planner.

## User stories

- US1: As an agent or skill author, I want to create an eval case by pasting a diff fragment and stating what the reviewer must find or must not flag, so that the set covers failures the agent has never produced.
- US2: As an agent or skill author, I want to edit a case, so that a wrong case is fixed without losing it and without silently changing what earlier runs mean.
- US3: As an agent or skill author, I want to run one case from the editor or the case list, and on save, so that I check a case in seconds without a full run.
- US4: As a skill author, I want my skill's own case set run through an agent I pick with the skill linked for that run, so that a skill edit is measured before it reaches every agent that links it.
- US5: As a skill author, I want the skill's metrics and run history with the agent and skill versions of each run, so that I know which change made the skill better or worse.

## Acceptance criteria (EARS)

- AC1 [US1]: WHEN the user activates "New eval case" on an agent's or a skill's Evals tab, the system shall open the Case Editor titled "New eval case" with the owner's name, an empty Name, an Input area with Diff, Files and PR meta tabs, an expectation type of `must_find` or `must_not_flag`, file, start line and end line, an Expected output editor, a Run on save toggle that is off until the user turns it on and then keeps its last setting in that browser, and the actions Cancel, Run case and Save.
- AC2 [US1]: WHEN the user pastes or types text into the Diff tab, the system shall show it as a diff preview with file headers, hunk headers, new-side line numbers and added and removed lines marked by "+" and "−" as well as colour, rendered as plain text, and list in the Files tab, read-only, every file path the diff changes with its added and removed line counts.
- AC3 [US1]: IF the diff is empty, longer than 100,000 characters, has no hunk, has a hunk whose line counts disagree with its header, or has a line outside a hunk that is not a file header, THEN the system shall refuse to save and show the reason with the number of the first offending line.
- AC4 [US1]: IF the PR meta title is longer than 300 characters or the description longer than 4,000 characters, THEN the system shall refuse to save and show the field's character counter against its limit.
- AC5 [US1]: IF the expectation's file is not a file of the diff, its start line is below 1 or above its end line, or its range intersects no hunk of that file on the new side, THEN the system shall refuse to save and name the reason.
- AC6 [US1]: The system shall show the badge "valid JSON" and allow Save only when the expected output is at most 20,000 characters of JSON that is `[]` for `must_not_flag`, or for `must_find` an array of exactly one object with a severity of CRITICAL, WARNING or SUGGESTION, a category of bug, security, perf, style or test, a title of 1–200 characters, and a file, start_line and optional end_line equal to the expectation's, and no other key — and otherwise show "invalid JSON" with the first reason and keep Save disabled.
- AC7 [US1]: WHEN the user activates "+ Finding skeleton" on a `must_find` case, the system shall replace the expected output with one finding object holding the expectation's file and lines, severity WARNING, category bug and an empty title, and show the action disabled with the hint "Nothing is expected for must_not_flag" on a `must_not_flag` case.
- AC8 [US1]: IF the name is empty, longer than 60 characters, contains anything but lowercase letters, digits and hyphens, or equals another case's name in the owner's set, THEN the system shall refuse to save and name the reason.
- AC9 [US1]: WHEN the user saves a valid new case, the system shall add it to the owner's set as a manual case whose stored input is exactly the diff and PR meta entered, used unchanged by every later run until the case is edited, and list it as "never run".
- AC10 [US2]: WHEN the user activates a case's edit action, the system shall open the Case Editor titled "Eval case · <name>" with the case's stored values, where a case created from a finding allows only its name to change and shows the hint "Created from a finding — input and expectation are fixed".
- AC11 [US2]: WHEN a save changes a case's diff, PR meta, expectation type, file, lines or expected output, the system shall store it as a new revision of that case, keeping every earlier revision that a run covered, while a change of name alone creates no revision.
- AC12 [US2]: The system shall record in every eval run the revision of each case it covered, and count a case covered at different revisions by the two runs of a comparison or alert as one removed and one added in the "Case sets differ: N added, M removed" notice (SPEC-05 AC19).
- AC13 [US2]: IF the latest completed run of the owner covered an earlier revision of a case, THEN the system shall show that case's row as "edited since last run" in place of that run's result.
- AC14 [US3]: WHEN the user activates Run case, a case row's run action, or Save with Run on save on, the system shall run that one case with the owner's current configuration (for a skill, as AC19 states) and show, without a page reload, "Last run passed|failed|errored · expected N finding(s), got M · <duration> · <cost>", with an em dash for an unknown cost and the reason for an errored case.
- AC15 [US3]: The system shall keep a single-case run out of the run history, the metric cards, the trend, the alert and every dashboard, store only the newest single-case result per case revision, and show in the editor's last-run strip the newer of that result and the case's result in the latest completed run.
- AC16 [US3]: IF the editor has unsaved changes, a single-case run of the same case is in progress, or the run-start rate limit is reached, THEN the system shall start no single-case run and show Run case disabled with the reason ("Save first", "Already running" or "Too many runs — try again in a minute").
- AC17 [US4]: The system shall show in the skill detail an Evals tab, after Preview, listing every case of the skill's set as the agent's Evals tab does (SPEC-04 AC8), with "x / N passing" from the latest completed run, Run all evals (the skill header's "Run on evals" is the same action), New eval case, and edit, run and delete actions on each row.
- AC18 [US4]: WHEN the user activates Run all evals or "Run on evals" on a skill with no remembered agent, or chooses "Change agent", the system shall ask for an agent of the workspace, remember the choice for that skill until it is changed, and show "via <agent name>" next to both actions while it is remembered.
- AC19 [US4]: WHEN a skill eval run starts, the system shall review each case with the remembered agent's current configuration and the skill's current version enabled for that run only — at its existing position when the agent links it, otherwise after the agent's other skills — without changing the agent's saved skills.
- AC20 [US4, US5]: WHEN a skill eval run starts, the system shall record with it the skill id and version, the agent id, name and version, and the rest of SPEC-04's run record (provider, model, system prompt, strategy, every linked skill with its version, the cases and their revisions).
- AC21 [US4]: IF the skill's set has no cases, a run of the same skill is in progress, or the remembered agent no longer exists, THEN the system shall start no run and show the reason, asking for an agent again with "<agent name> no longer exists" in the last case.
- AC22 [US5]: WHILE the skill has a completed eval run, the system shall show on its Evals tab the metric cards and run history of SPEC-04 AC23 and AC24, each history row also naming the agent and its version and the skill version, an agent shown as "<name> (deleted)" once deleted.
- AC23 [US4]: WHEN a skill is deleted, the system shall delete its cases, their revisions and its eval runs and single-case results, and keep the skill eval runs made through an agent when only that agent is deleted.
- AC24 [US1, US2, US3, US4, US5]: IF a case, skill, agent or run named in a request is outside the caller's workspace, or a case is named under an owner it does not belong to, THEN the system shall answer "not found", change nothing and make no model request.
- AC25 [US1, US3]: The system shall send to the model, for a case, only its diff and PR title and description through the review engine's untrusted slots and injection guard (SPEC-04 AC13), and never its name, notes or expected output.

## Edge cases

- EC1: A pasted diff has no `diff --git` line, only `---`/`+++` headers as in `images/13.png` — accepted (covered by AC3).
- EC2: A pasted diff of 120,000 characters — refused with the limit named (covered by AC3).
- EC3: A hunk header says `+10,7` but the body has 5 new-side lines — refused with the hunk's line number (covered by AC3).
- EC4: A line `random text` sits between two hunks — refused with its line number (covered by AC3).
- EC5: A diff touching three files — all three listed in Files; the expectation may name any of them (covered by AC2, AC5).
- EC6: The expectation names line 300 of a file whose only hunk covers lines 10–17 — refused (covered by AC5).
- EC7: Expected output pasted as `{"severity": "CRITICAL", ...}` without the array — "invalid JSON" with the reason (covered by AC6).
- EC8: Expected output with a `__proto__` or `instructions` key — refused as an unknown key (covered by AC6).
- EC9: Expected output's `start_line` 12 while the expectation says 14 — refused (covered by AC6).
- EC10: Expectation type switched from `must_find` to `must_not_flag` with a finding in the JSON — "invalid JSON" until it is `[]` (covered by AC6, AC7).
- EC11: Two cases named `stripe-key-leak` in one set — the second is refused; the same name in another owner's set is allowed (covered by AC8).
- EC12: A case created from a finding is opened for edit — only the name can change (covered by AC10).
- EC13: Only the name of a manual case is changed — no new revision and no "edited since last run" (covered by AC11, AC13).
- EC14: A case is edited while a run that covers it is in progress — the run keeps the revision recorded at its start (covered by AC12; SPEC-04 AC14).
- EC15: v6 ran 20 cases, one was edited, v7 ran the same 20 — "Case sets differ: 1 added, 1 removed" (covered by AC12).
- EC16: Run case pressed twice quickly — the second press is refused while the first runs (covered by AC16).
- EC17: Run case while the agent's full eval run is in progress — allowed; the result does not enter the run history (covered by AC14, AC15).
- EC18: The provider key is missing — the single-case run shows "Last run errored" with the reason (covered by AC14).
- EC19: A skill run through an agent that already links the skill but has it switched off — the skill is on for that run only, at its position (covered by AC19).
- EC20: A skill disabled on the skill list — still included in its own eval runs (covered by AC19).
- EC21: The remembered agent was deleted — Run all evals asks for an agent again, naming the deleted one (covered by AC21).
- EC22: A skill run and the picked agent's own run at the same time — both proceed; each records its own configuration (covered by AC19, AC20).
- EC23: A skill is edited during its run — the run keeps the skill version recorded at its start (covered by AC20).
- EC24: The skill is deleted — its Evals tab, cases and runs disappear (covered by AC23).
- EC25: A case id of a skill used under an agent's route — "not found" (covered by AC24).
- EC26: The pasted diff contains "ignore previous instructions" — it reaches the model only through the engine's guard, like any review (covered by AC25).

## Non-functional requirements

- **Sizes.** Diff at most 100,000 characters, as SPEC-04's frozen input (AC3); PR title at most 300 characters, a limit new to this spec (SPEC-04 caps no frozen title), and description at most 4,000 characters, as SPEC-04 AC4; both optional (AC4); expected output at most 20,000 characters and a finding title at most 200 (AC6); name at most 60 characters, as SPEC-04 AC5 (AC8).
- **Validation parity.** Every rule in AC3, AC4, AC5, AC6 and AC8 is enforced by the server on every save, whatever the client sends; the editor shows the same rules while typing so a valid form never fails on save for a rule it could have shown.
- **Model calls.** Validation and scoring make no model request. A single-case run makes the requests one review of that case makes through the review engine, re-asks included, and nothing else.
- **Concurrency and rate.** Skill runs follow SPEC-04's rules per skill: at most 3 cases at a time and one run per skill; a skill run does not block, and is not blocked by, the picked agent's own run. A single-case run is limited to one per case at a time. Starting a full run, a skill run or a single-case run counts against the same 10 starts per minute.
- **Latency.** The diff preview and the JSON badge update within 300 ms after the user stops typing, for a 100,000-character diff on the local stack. A single-case run answers before the review finishes and its result appears without a page reload, refreshed at least every 5 seconds.
- **History.** Case revisions are append-only while a run refers to them; the per-case result of a past run never changes after an edit (AC11, AC12).
- **Tenancy.** Every request is scoped to the caller's workspace and the case's owner (AC24).
- **Cost.** Unknown cost is an em dash, never "$0"; a free model is "$0" (SPEC-04 › Cost).
- **Logging.** No diff, expected output, name or notes in logs.
- **Contract reach.** The case shape today has no expectation type, no expectation location, no origin (manual or from a finding) and no revision; those facts change in both `vendor/shared` copies together, whose eval sections are identical today.
- **Accessibility.** The JSON badge, row states and the last-run strip carry text and icon, never colour alone; diff lines carry "+"/"−"; every editor control is reachable by keyboard and the dialog returns focus to the row that opened it.
- **i18n.** Every label comes from the `eval` namespace (`client/messages/en/eval.json`, which already holds `caseEditor` and `evalsTab` keys) or the `skills` namespace for the tab label; English only.

## Untrusted inputs

| input | handling | AC |
|---|---|---|
| Pasted diff (any text, possibly copied from an untrusted PR) | size-capped; parsed strictly, refused on malformed hunks or stray lines; rendered as plain text; reaches the model only through the engine's untrusted slot and injection guard; never logged | AC2, AC3, AC25 |
| PR title and description typed in PR meta | length-capped; sent only as the engine's untrusted slots | AC4, AC25 |
| Expected output JSON typed by the user | size-capped; only the listed keys and values accepted, unknown keys (including `__proto__`) refused; must agree with the expectation; never sent to the model; shown as plain text | AC6, AC25 |
| Case name | restricted alphabet and length; unique per set; never sent to the model | AC8, AC25 |
| Expectation file and lines | must name a file of the diff and intersect a hunk | AC5 |
| Model output during a single-case or skill run | grounded and scored by SPEC-04's code-only rules | AC14, AC19 |
| Case, skill, agent and run ids in requests | must belong to the caller's workspace and the named owner; otherwise "not found", no model request | AC24 |
| Repeated single-case and skill run starts (cost exposure) | one in progress per case and per skill; shared 10-per-minute start limit | AC16, AC21 |
